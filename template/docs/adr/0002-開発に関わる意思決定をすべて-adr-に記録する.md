# 2. 開発に関わる意思決定をすべて ADR に記録する

Date: 2026-11-24

## Status

Accepted

## Context

実装の中で決めたことを 1 つのファイルに時系列で追記すると、後から改められた判断と現在も有効な判断が同じ形で並ぶ。ある判断が現在も有効かどうかは、後の日付の記録をすべて読まないと分からない。選択肢を比べた経緯が書かれていないと、なぜ他の方法にしなかったのかを、あとから確かめられない。

## Decision

- 開発に関わる意思決定(構成、技術の選定、規約、データや API の形、画面の仕様と見た目、テスト、デプロイと運用、障害への対処)は、すべて `docs/adr/` に ADR として記録し、[adrs](https://github.com/joshrotenberg/adrs) で管理する。形式は Nygard、モードは adr-tools 互換(`.adr-dir`)とする。記録先が 1 つになり、判断が現在も有効かどうかを Status で確かめられる
- 他の選択肢を検討したうえで決めた判断には、Decision の中に `### Alternatives` の子見出しを置き、採用しなかった案と、採用しなかった理由を書く
- エージェントが自分で下した判断は Status を Proposed にし、人間が確認して Accepted にする。人間の判断が必要で決められなかった点は、その ADR の Consequences に「要確認:」として書く
- 判断を改めるときは、元の ADR を書き換えず、新しい ADR を作って元の ADR を Superseded にする

### Alternatives

- 不採用: `docs/decisions.md` に、すべてを時系列で書き続ける。改められた判断と有効な判断が、同じ形で並ぶ

## Consequences

- 書き方と確認の手順は `docs/workflow.md` の「判断の記録」と「未確認の判断の確認」に従う
- ADR を作成・変更するには、開発者が adrs の CLI をインストールしておく。lefthook と CI が `adrs doctor --warnings-as-errors` で検査する
