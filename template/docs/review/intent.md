# レビューの観点: 意図・要件・判断の記録

PR の本文・`docs/requirements.md`・ADR と、変更を突き合わせて確かめる観点。`find` の担当 `intent` に渡す。

## 範囲・要件・判断の記録(すべての PR)

- 変更が PR の title と本文に書かれた範囲に収まっている。範囲外の変更や、要件にない先回りの実装がない
- 差分が本文に書かれた意図に沿っている。次の 3 つを指摘にする
  - 意図のどれにも対応しない変更(本文に書かれていない変更)
  - 本文の説明と異なる実装
  - 本文に書かれているのに、差分に無い変更
- 要件 ID のある変更は、`docs/requirements.md` のその要件の記述を満たしている
- 仕様の変更があるときは、`docs/requirements.md` が同じ PR で更新されている
- 判断を伴う変更(構成、依存の選定、規約、データや API の形、画面の仕様、テスト、デプロイと運用)には、`docs/adr/` に ADR が追加されている
- 変更が、Status が Accepted か Proposed の ADR の判断と矛盾していない。判断を改める変更は、`-s` で元の ADR を Superseded にする新しい ADR を含んでいる
- セットアップやコマンドの変更が、`CLAUDE.md` と `README.md` に反映されている

## PR とコミット(すべての PR)

- title が `<prefix>: <日本語の常体>(要件 ID)` の書式になっている。title は squash マージで main のコミットメッセージになるため、コミットメッセージと同じ書式にする
- prefix が、触ったファイルではなく、利用者から見て何が変わるかで選ばれている(`docs/workflow.md` の「prefix の選び方」)。
  画面や meta 情報に出る文字列の変更は `feat`、不具合の修正でないものに `fix` を使っていない
- 本文に、変更した理由(何が問題で、何をどう変えたか)が書かれている
- base ブランチが main で、他の PR のブランチから派生していない
- ブランチ名の type と名前が、変更の中身に合っている。type は、title の prefix と同じく利用者から見て何が変わるかで選び(`docs/workflow.md` の「prefix の選び方」)、名前は変更の主題を表す。たとえば、テストの再編を `docs/` のブランチで行っていたり、名前が変更と別の主題を指していたりすれば指摘する
- 追加した依存が、`docs/workflow.md` の「依存パッケージ」にある採用済みのスタックか、その公式の周辺パッケージである。
  それ以外の依存は追加されておらず、ADR に提案として書かれ、人間が Accepted か Rejected にしている。バージョン指定に `~` が付いている
- テーブル定義(`apps/api/src/db/schema.ts`)を変えた PR に、`apps/api/drizzle/` のマイグレーションが含まれている

## ADR(`docs/adr/**` を変えた PR)

`docs/workflow.md` の「判断の記録」と突き合わせる。

- 1 つの ADR の主題が 1 つで、タイトルが判断の内容の分かる日本語の文になっている
- 他の選択肢を検討した判断には `### Alternatives` があり、採用しなかった案ごとに理由が書かれている。採用した案の理由は Decision に書かれている
- 理由に、そうなる仕組みが書かれている。指示で決まった判断にも、指示した人が挙げた理由か、誰が何を決めたのかが書かれている
- 「要確認」に書かれているのが、人間の判断が要る点だけになっている
- Status が Proposed の ADR が残っていない。エージェントが自分で下した判断の ADR は、push の前に人間が確認し、Accepted にしているか、人間の指示に従って新しい ADR で Superseded にしているか、依存の提案なら Rejected にしている
- 既存の ADR の判断を改めるときに、元の ADR の本文を書き換えず、新しい ADR で Superseded にしている
