# レビューの共通の基準

`.github/workflows/claude-code-review.yml` の、指摘を出す段階(`find`)と指摘を検証する段階(`verify`)の両方に渡す基準。
規約の本文は `CLAUDE.md` と `docs/workflow.md` にあり、`docs/review/` には、規約のうちレビューで確かめるものと、確かめるときに開くファイルだけを書く。

## 指摘の対象

CI(`ci.yml`)と lefthook が検査するものを指摘すると同じ失敗が 2 か所で報告されるので、指摘の対象は、規約・要件・正しさのうち、CI と lefthook が検査できないものに限る。対象は次の 2 種類である。

- 意味を読まないと判断できないもの(名前が中身に合っているか、コメントが理由を書いているか、変更が要件を満たしているか)
- 差分の外のファイルと突き合わせないと分からないもの(表への追加漏れ、`docs/requirements.md` や ADR との不一致)

ESLint・typecheck・depcruise・テスト・commitlint・`adrs doctor` が失敗として報告するものは、指摘しない。
見た目とデザインカンプの一致は、作業者が `docs/workflow.md` の「検証」に従ってブラウザで確かめるため、指摘しない。
見た目に関わる変更では、PR の本文に、確認した画面・幅・配色が書かれているかだけを見る。

## 指摘の基準

- 差分と、開いたファイルを読んで確かめたものだけを指摘する。推測で指摘しない
- PR の本文は、変更の意図として読み、差分が意図に沿っているかの基準にする。本文に書かれた検証の結果(「確認した」「影響しない」)は、正しいかを本文から判断できないため、コードとテストを読んで確かめる。
  本文に書かれていることを、指摘しない理由にしない
- 規約にも要件にも根拠のない、書き方の好みは指摘しない
- PR が変更していない行の既存の問題は指摘しない。変更によって新たに規約と合わなくなった箇所(表への追加漏れなど)は指摘する
- `gh pr view --comments` のコメントで指摘済みのものは、繰り返さない
- 変更に関わる既存の判断は adrs の MCP ツールで探し、見つかった ADR の本文を読む。Status が Superseded の ADR は改められた判断なので、指摘の根拠にせず、`get_related_adrs` で改めた側の ADR をたどって読む

## 指摘の項目

指摘は、出力の `findings` に次の項目で並べる。インラインコメントと要約は、ワークフローのスクリプトがこの項目から組み立てるため、項目に Markdown の見出しや `**[修正が必要]**` のような種類の表示を書かない。

- `kind`: 修正が必要なら `must`、提案なら `suggest`。修正が必要は、規約の違反、不具合、要件を満たしていない点。
  提案は、規約にはないが直したほうがよい点で、`detail` に理由を書く
- `path`・`line`: 指摘する行。PR の変更後のファイルの行番号にする。行に結び付かない指摘は両方 null にする
- `title`: 指摘を 1 文にまとめたもの
- `basis`: 根拠。規約の違反は `CLAUDE.md`・`docs/workflow.md` の節の名前か ADR の番号(`docs/adr/0089`)、不具合は誤った結果になる入力や状態
- `detail`: どのファイルのどの記述が、どの条件で、規約や要件にどう合わないか
- `suggestion`: 行の置き換えで修正を示せるときは、置き換え後の行。示せないときは null

文章は日本語で、`CLAUDE.md` の「文章」に従って書く。比喩、話し言葉、絵文字、中身のない強調や称賛は書かない。
